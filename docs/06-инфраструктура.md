# Репозиторий, данные и совместная работа

## Короткий ответ

Код — в git. Данные — **не в git**. Между ними — конфигурация среза и манифест
с контрольными суммами, по которым любой участник воспроизводит выгрузку у себя.

## Почему данные не помещаются в GitHub

| Ограничение | Значение |
|---|---|
| Файл больше 100 МБ | отклоняется при push |
| Предупреждение | с 50 МБ |
| Рекомендованный размер репозитория | до 1 ГБ |
| Git LFS в бесплатном тарифе | 1 ГБ хранилища и 1 ГБ трафика в месяц |

Наш корпус — гигабайты, поэтому в репозиторий он не поместится ни целиком, ни через LFS.
И не должен: git хранит историю всех версий файла, а бинарная выгрузка, положенная в git
хотя бы раз, останется в истории навсегда и утяжелит клонирование для всех.

## Порядок величин

| Что | Размер |
|---|---|
| Срез научных работ по направлению за 15 лет, ~1 млн записей, только нужные поля | 1–1,5 ГБ в JSON, 300–500 МБ в parquet |
| Векторные представления того же объёма | ~1,5 ГБ (float32), вдвое меньше в float16 |
| Готовый индекс: кластеры, признаки, топ, тексты карточек | единицы мегабайт |
| Тестовая подвыборка (20–50 тыс. записей) | 10–30 МБ |

Ключевое следствие: **тяжёлое считается один раз, а команда работает с лёгким**.
Фронтенду и бэкенду корпус не нужен вообще — им нужен готовый индекс, а он мегабайтный
и спокойно лежит в репозитории.

## Что где лежит

**В репозитории:**

- весь код;
- `config/` — параметры среза: направление, диапазон лет, версия источника, версия модели
  представлений, значения порогов. Это и есть описание того, какие данные считаются
  «нашими»;
- `data/manifest.json` — список файлов среза с размерами и контрольными суммами;
- `data/sample/` — тестовая подвыборка, десятки мегабайт. Нужна, чтобы тесты и проверки
  запускались у всех и в любой момент;
- `artifacts/` — готовый индекс: кластеры, признаки, топ-15, карточки. Мегабайты,
  версионируются вместе с кодом, который их породил.

**Вне репозитория:**

- полный срез и векторные представления — общая папка в облаке;
- всё, что перечислено в `.gitignore`.

## Как синхронизировать данные

Три варианта по возрастанию сложности. Для двух недель достаточно первого.

**1. Общая папка в облачном диске.** Один архив со срезом, один с представлениями.
Бесплатных 15 ГБ хватает с запасом. Минус — ручное скачивание, плюс — работает сразу
и не требует настройки.

**2. Объектное хранилище с оплатой по объёму** (S3-совместимое). Порядка 2 ₽ за гигабайт
в месяц: 50 ГБ обойдутся примерно в 100 ₽. Синхронизация одной командой, скачивается
только изменившееся. Имеет смысл, если срезов станет несколько.

**3. Ничего не синхронизировать.** В репозитории лежит конфигурация среза и скрипт
выгрузки, каждый воспроизводит корпус у себя. Честно, но расточительно: выгрузка занимает
часы, а результат у всех одинаковый.

Рекомендация: вариант 1 плюс манифест с контрольными суммами в git, чтобы можно было
проверить, что у всех один и тот же срез. Расхождение в данных — самая трудноуловимая
причина «у меня работает, у тебя нет».

## Как тестировать

- **На подвыборке.** Весь конвейер должен запускаться в режиме `--sample` на данных
  из `data/sample/` за секунды. Это то, что гоняется при каждом изменении.
- **Полный прогон** делает один человек на своей машине и кладёт результат
  в `artifacts/`. Остальные работают с готовым индексом.
- **Фиксированные значения генератора случайных чисел** во всех местах, где есть
  случайность (снижение размерности, кластеризация). Иначе два запуска дадут разные
  кластеры и сравнивать будет нечего.
- **Проверка воспроизводимости**: один скрипт, который из конфигурации и среза получает
  итоговые цифры. Если он проходит от начала до конца, решение можно защищать.

## Нужно ли что-то покупать

Скорее нет.

- **Хранилище** — бесплатных облачных 15 ГБ достаточно. Объектное хранилище за ~100 ₽
  в месяц имеет смысл только ради удобства синхронизации.
- **Вычисления** — векторные представления для миллиона коротких текстов считаются на
  видеокарте за час-два, на процессоре ноутбука за ночь. Бесплатные тетради с доступом
  к видеокарте (Kaggle даёт около 30 часов в неделю) закрывают эту задачу полностью.
  Покупать вычисления не нужно.
- **Данные** — все перечисленные источники открыты и бесплатны. Платными бывают
  отраслевые аналитические отчёты, но как эталон они нам не подходят.

Единственная статья, где деньги действительно могут понадобиться, — облачные выгрузки
больших наборов с оплатой по объёму запроса. Их проще ограничить выборкой, чем оплачивать.

## Работа через git

Да, через git, и это не формальность: без него пять человек за две недели гарантированно
затрут друг другу правки.

Договорённости, которых достаточно:

- одна основная ветка, короткие ветки под задачи, слияние по готовности;
- данные и артефакты тяжелее мегабайта не коммитятся — за этим следит `.gitignore`;
- имена файлов конфигурации и артефактов содержат версию среза, чтобы результаты
  разных прогонов не путались;
- перед слиянием прогоняется конвейер на подвыборке.
